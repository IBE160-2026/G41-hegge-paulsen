## Intent

**Problem:** The only way to request a workout suggestion is the menu form, and the result renders inline on the same page as the input. The user wants a free-text alternative to the menu, and wants the resulting suggestion to appear on its own page rather than inline.

**Approach:** Add a chat/free-text input on the landing page, alongside (not replacing) the existing `#workout-form` menu. A new pure-function parser (`chatParser.js`) maps Norwegian free text to the same six inputs the menu already collects (time, focus, energy, trainingMode, level, equipment) via simple keyword/pattern matching — no external AI/LLM API, matching this project's documented MVP boundary against external API keys and complex AI features. Anything the parser can't recognize in the text falls back to the same default the menu form itself uses for that field (time 30, focus styrke, energy medium, trainingMode home-dumbbell, level intermediate, equipment empty) — never an error, just the form's own defaults. The chat form and the menu form are independent, decoupled input paths to the same `getWorkoutSuggestion` call; submitting one never reads or writes the other's fields.

Moving the result to its own page reuses the exact mechanism the account page already uses: a `?view=...` query-param read once at page load (`?view=forslag`), toggling a body class that a CSS rule uses to show/hide sections — not a new HTML file, not a client-side router. Since that mechanism only evaluates on load (a real navigation, not a SPA transition), the generated suggestion must be persisted to `localStorage` (mirroring the existing history/weekly-plan pattern) before navigating, so the new page's load can read and render it. Only the suggestion result card moves to the new page — the next-weight and progress cards, which currently share `#results` with it, stay on the landing page; the user named the suggestion specifically, and moving the others would be a bigger surprise than leaving them.

**Human decisions (2026-10-19):**
1. Chatbot type: a simple rule-based text-to-selection parser, not an AI/LLM-backed chatbot.
2. New page mechanism: the same `?view=...` pattern already used for the account page, not a separate HTML file.
3. Chatbot coverage: full coverage of everything the menu form can set — a genuine equal alternative, not a limited subset.

## Boundaries & Constraints

**Always:**
- `parseWorkoutRequest(text)` returns `{ time, focus, energy, trainingMode, level, equipment }` with every field defaulted to the menu form's own default value when not recognized in `text`; never throws, never returns a field as `null`/`undefined`.
- Keyword matching is case-insensitive and tolerant of Norwegian compound/variant phrasing (e.g. both "styrke" and "styrketrening" match focus=styrke). Where "middels" could plausibly match either energy or level, only match it for energy (`"middels energi"`/bare "middels") — level only matches the more specific "nybegynner"/"erfaren"/"viderekommet", since "intermediate" is already the form's default and needs no explicit trigger.
- Submitting either `#workout-form` or the new chat form: compute the suggestion, persist it via a new local (not exported, ui.js-internal) `localStorage` read/write pair under a new key, then navigate with `window.location.href = '?view=forslag'` -- a real navigation, matching the account-page link's existing behavior, not a `pushState`/in-place DOM swap.
- On `?view=forslag` load: read the persisted suggestion and render it with the existing `renderSuggestion`/`getDisplayExerciseDetails`/`renderExerciseListItems` functions, unchanged. If nothing is persisted yet (e.g. a bare/bookmarked `?view=forslag` visit), show an empty/prompt state in the result card instead of erroring (mirroring the weekly-plan section's existing empty-state convention).
- The existing `#account-navigation` link's toggle logic extends to cover the new page the same way it already covers the account page: show "Tilbake til økt" / `href="/"` when on `?view=forslag` OR `?view=account`, "Konto" / `href="?view=account"` otherwise.
- **(Renegotiated 2026-10-19, see Spec Change Log)** The landing page (plain, no `?view=`) shows only the account panel, the menu form, and the chat section. Every other section -- the suggestion card, `#results` (next-weight + progress/weekly-guideline), the log form, and the weekly-plan section -- is visible only on `?view=forslag`. This is a CSS-only reorganization (`body:not(.suggestion-page)` hides those four sections, `body.suggestion-page` hides the account panel/menu/chat instead); no change to the JS that renders any of them.

**Never:**
- Do not call any external AI/LLM API or add a new dependency for natural-language parsing -- keyword/pattern matching only.
- Do not make the chat form read or write `userProfile`'s equipment, call `saveProfileEquipment`, or otherwise touch the menu form's own fields/checkboxes -- for `trainingMode: 'custom'`, use only equipment the parser itself recognized in the text (empty list if none, which already degrades gracefully via `getWorkoutSuggestion`'s existing "no equipment selected" message).
- Do not change `getWorkoutSuggestion`'s signature or logic -- both input paths call it exactly as it exists today.

## Implementation Notes

- `parseWorkoutRequest` gates equipment extraction on the detected `trainingMode` being `'custom'` -- for every other mode it returns `equipment: []` even when an equipment word (e.g. "manualer") also happens to be the word that triggered that mode (e.g. `home-dumbbell`). This is what makes row 1 of the I/O matrix (`"...hjemme med manualer..."` → `equipment: []`, not `['dumbbell']`) and the "never populates equipment for a non-custom training mode" case both hold, and matches the Boundaries' "for `trainingMode: 'custom'`, use only equipment the parser itself recognized" wording.
- Equipment keyword-to-id mapping deliberately uses the more specific Norwegian terms (`vektstang`, `styrkeapparat`) rather than generic substrings (`stang`, `apparat`) so that e.g. `pull-up-stang` never also triggers `barbell`, and `kabelapparat` never also triggers `machine`.
- `"middels"` only ever resolves `energy`; no keyword list exists that could resolve `level` to `'intermediate'` from it, per the Boundaries' explicit ambiguity rule. `level` is only ever set away from its default by the more specific `nybegynner`/`erfaren`/`viderekommet`.
- `updateView()` gained a `return suggestion;` at its end (the one deviation from "unchanged") so the `#workout-form` submit handler can persist the exact object that was just rendered without recomputing it or duplicating `getWorkoutSuggestion`'s call-site wiring. Its existing behavior (next-weight/progress computing and rendering, custom-equipment profile sync) is otherwise untouched.
- The page's unconditional load-time `updateView()` call (computing a suggestion from the menu form's current/default selections) still runs on every page load, including `?view=forslag`, exactly as it did before this change -- the new `if (suggestionPage) { ... }` block was placed immediately after it so it overwrites that default render with the actually-persisted suggestion (or the empty state) by the time the page is visible. `updateView()` has no first `await` on the default (non-custom) path, so this ordering is reliable without an explicit synchronization mechanism, consistent with the pre-existing pattern the rest of this file already relies on (see `tests/ui.test.js`'s `renderApp()` helper comment).
- Added integration tests to the existing `tests/ui.test.js` (not called out in the spec's Code Map, which only listed the new `tests/chat-parser.test.js`) covering: `#workout-form` submit persisting the suggestion, `#chat-form` submit parsing free text and persisting the equivalent suggestion, the chat path never touching `smartokt-user-profile`, a direct `?view=forslag` visit rendering a previously-persisted suggestion, the bare-visit empty state, and the `#account-navigation` label/href toggle on the suggestion page. These exercise the spec's acceptance criteria beyond what the pure-function parser tests alone can cover.
- `window.location.href = '?view=forslag'` under jsdom (the test environment) logs a harmless "Not implemented: navigation to another Document" to stderr and does not actually change `window.location` -- expected jsdom behavior, not a test failure; verified the assignment itself (and the persistence that precedes it) still executes correctly by asserting on `localStorage` content immediately after dispatching each submit event.

## Review Triage Log

- **high, patch** -- `updateView()` unconditionally called `renderSuggestion(suggestion)`. `applySession`'s guest branch, its signed-in branch (before the `loadProfile` await resolves), and its catch branch each fire `void updateView()` asynchronously; all three run after the module's synchronous top-level code (including the `?view=forslag` load-time render-or-empty-state block) whenever `supabase` is non-null (i.e. configured). That meant a correctly-rendered persisted suggestion on the suggestion page got silently overwritten moments later with a freshly-computed suggestion from the menu form's current/default state -- breaking the feature for any Supabase-configured deployment. Fixed by guarding the call: `if (!suggestionPage) { renderSuggestion(suggestion); }`. `updateView()` still returns the computed suggestion unchanged and still renders next-weight/progress unconditionally.
- **medium, patch** -- `parseEquipment` ordered extracted equipment by where each word first appeared in the free text, but `getWorkoutSuggestion`'s custom-mode exercise selection is order-sensitive, and the menu form's checkboxes always produce equipment in `profileEquipmentOptions`'s declared order regardless of click order. Chat and menu text could therefore describe the same logical equipment set and get different suggestions, contradicting the Acceptance Criteria's "matches what the menu form would produce for the equivalent explicit selections." Fixed by sorting matched ids by position in `profileEquipmentOptions` instead of text-mention position (see Spec Change Log for the one frozen I/O-matrix value this corrects).
- **medium, patch** -- `parseTrainingMode`'s `'gym'` check was a bare substring match, so `"gymnastikk i dag"` (and any other word merely containing "gym") resolved `trainingMode: 'gym'`.
